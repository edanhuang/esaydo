# EasyDo Bot 派发设计

> 状态（2026-10-28）：第一版已实现，并提前接入了 Codex；改动归属与 worktree、系统通知、空闲看门狗尚未实现。
> 参考：[multica](https://github.com/multica-ai/multica) 的「把 Issue 交给本地 Agent」链路，只借鉴设计，不复用代码（其许可证对商业嵌入有附加条款）。

## 1. 目标

把一条 Todo 交给本地安装的 AI（Claude Code、Codex）去做，EasyDo 负责：

- 用固定配置的 Bot 发起和延续对话；
- 在看板上标出哪些 Todo 正在被 Bot 处理；
- 收下 Bot 交回的结果，提醒用户查看，并能接着对话。

**不做的事**：EasyDo 不承接 Bot 的完整过程输出。思考、工具调用、中间回复都去对应 AI 的 App 里看，EasyDo 只保存每次运行的最终回复和会话信息。

### 1.1 为什么不直接用 multica

- multica 面向团队，由 Go 服务端、PostgreSQL、网页端、本地守护进程组成。用云服务时任务内容要上传第三方，自部署又要维护 Docker 和数据库。EasyDo 是单机、本地优先的个人工具。
- 两套任务体系（multica Issue 和 EasyDo Todo）需要同步，状态容易对不上。
- EasyDo 已有 `easydo` CLI、easydo Skill 和后台同步脚本（`scripts/agent-sync/worker.py` 已经在用 `claude -p` 无界面调用），派发需要的基础大多已经具备。

## 2. 概念

| 概念 | 说明 |
|---|---|
| Bot | 用户手动新建的执行者，固定了 AI、模型、工作目录 |
| 会话 | 一个 Todo 在一个 Bot 下的对话，对应 AI 平台里的一个会话 ID；同一对 Todo × Bot 只有一个会话 |
| 运行 | 一次派发（或一次在消息里的回复）启动的一次 AI 进程 |
| 消息 | 会话里的往来记录：用户发出的说明，和每次运行的最终回复 |

## 3. Bot 管理

### 3.1 入口

侧栏新增一项「Bot」，图标用机器人（lucide `Bot`），进入独立的 Bot 页面。

### 3.2 字段

| 字段 | 说明 |
|---|---|
| 名称 | 显示在头像旁、消息列表里 |
| 颜色 | 从预设色板选择（见 3.4），用于渲染头像图标和运行时的卡片投影。头像是 lucide `Bot` 图标（只有机器人头部，不带身子），图标用 Bot 颜色，垫一个 20px、圆角 5px 的圆角方形底，底色用同色 14% 透明度 |
| AI | `claude` 或 `codex`（本机都已安装） |
| 模型 | 按所选 AI 提供常用选项，也可手填 |
| 目录 | 文件夹选择器选择 Bot 干活的目录 |
| Token 用量 | 只读展示：累计用量，以及每次运行的明细 |

### 3.3 规则

- Bot 必须手动新建，没有默认 Bot。
- Bot 有运行中的任务时，不能删除，也不能改 AI 和目录。
- 改了 AI 或目录后，该 Bot 名下已有的会话都无法延续（见 5.2），下一次派发会新开会话，并在消息里提示「已换成新会话，之前的上下文不会带过去」。只改模型不影响会话。
- 删除 Bot 时，它名下的会话、运行记录、消息一起删除。删除前二次确认，并写明会删掉多少条消息。AI 平台里的原会话不受影响。

### 3.4 预设色板

8 种颜色，与 Terrazzo 主题的暖色调协调。刻意避开主题重点色（铁锈红），以免和选中描边、高优底色混淆。每种颜色配浅色、深色主题两套值（HSL）：

| 名称 | 浅色主题 | 深色主题 |
|---|---|---|
| 琥珀 | `36 72% 40%` | `38 70% 60%` |
| 橄榄 | `75 32% 34%` | `74 30% 58%` |
| 苔绿 | `145 30% 34%` | `145 28% 56%` |
| 青 | `182 38% 32%` | `180 32% 56%` |
| 靛蓝 | `222 38% 46%` | `222 50% 68%` |
| 梅紫 | `300 22% 42%` | `300 24% 66%` |
| 玫红 | `350 45% 46%` | `350 55% 70%` |
| 石墨 | `30 5% 36%` | `34 6% 62%` |

颜色选项里第一个是「随机」（色相转一圈的炫彩图标），新建 Bot 时默认选它。保存时才定下具体颜色：从还没被其他 Bot 用过的颜色里随机挑；8 种都用过时，从被用得最少的几种里随机挑。

对比度已核对（对页面底色和卡片底色取较低值）：浅色主题 3.5–5.9，深色主题 6.1–8.0，均高于图标所需的 3:1。最低的是浅色主题下的琥珀（3.5）。

## 4. 派发

### 4.1 入口

- 卡片和列表行的右键菜单增加「派发给 Bot ›」，子菜单列出所有 Bot。
- 还没有任何 Bot 时，子菜单只有「新建 Bot…」，点击跳到 Bot 页面。
- 消息会话窗里输入内容并发送，等同于一次派发（延续同一会话）。

### 4.2 派发弹窗

- 显示 Bot 的头像、名称、目录。
- 已有会话时显示「将继续上次的会话：<会话标题>」。
- 一个可选的「补充说明」输入框；不填就用 Todo 的内容。
- 需要 worktree 时，在这里插入第 6 节的说明步骤。

### 4.3 限制

- 同一对 Todo × Bot 已经有运行中的任务时，不能再派发，也不能在会话窗里发送。
- 已完成、已归档的 Todo 不能派发。

## 5. 会话

### 5.1 复用

- 会话以 Todo × Bot 为键，记录 AI 类型、会话 ID、会话标题、实际工作目录（原目录或 worktree 路径）。
- 第一次派发新建会话，之后每次派发、每次在会话窗回复都用同一个会话 ID 续上。
- 同一个 Todo 派给不同 Bot，各自独立。

### 5.2 会话与目录绑定

Claude Code 按工作目录存会话，换目录后原会话 ID 无法续上。因此：

- 一个会话第一次在哪个目录跑（原目录或某个 worktree），之后固定在那里跑。
- Bot 改了目录或 AI 后，旧会话作废，下次新开。

### 5.3 会话标题

- **Claude Code**：新建会话时用 `-n/--name` 起名，格式为「EasyDo · <Todo 主句>」，在 Claude 的会话列表里一眼能认出来。用户在 Claude 里改名后，名字会写进会话文件（`custom-title` 记录），EasyDo 读回最新标题展示。
- **Codex**：`codex exec` 没有起名参数（已实测，codex-cli 0.163.0）。通过 `exec` 新建的会话，标题就是第一条提示词的全文。因此 EasyDo 拼提示词时把「EasyDo · <Todo 主句>」放在第一行，附加说明放在后面，Codex 的会话列表里第一行就能认出来。标题从 Codex 的本地索引只读获取：优先 `~/.codex/session_index.jsonl` 的 `thread_name`（用户在 Codex 里改过名时才有），否则用 `~/.codex/state_5.sqlite` 的 `threads.title`。这两处都是 Codex 的内部存储，版本升级可能变化，读不到时退回 EasyDo 自己拼的标题。multica 通过 Codex 的 app-server 接口给会话起名，以后需要时可以照做。

## 6. worktree

### 6.1 原则

默认直接在 Bot 的目录里跑，不开 worktree。只有当目录里存在「不属于这段会话」的未提交改动时，才说明原因、征得用户同意后开启。目录不是 git 仓库时，一律直接跑。

### 6.2 改动归属

为了不让 Bot 被自己留下的改动打扰，EasyDo 记录每个未提交文件是谁改的：

1. 每次运行开始前和结束后，各记一次目录内未提交文件（含未跟踪文件，不含被忽略的文件）的内容指纹。
2. 运行期间新出现或内容变化的文件，记在这段会话（Todo × Bot）名下，连同结束时的内容指纹。
3. 文件不再处于未提交状态（已提交或已还原）时，清掉它的归属记录。

### 6.3 派发时的判断

逐个检查当前未提交的文件：

| 文件状态 | 处理 |
|---|---|
| 归属于本会话，且内容与记录一致 | 忽略，直接跑 |
| 用户的改动：从未被 Bot 改过，或 Bot 改完后内容又变了 | 弹窗说明，建议开 worktree |
| 归属于其他会话（别的 Bot，或同一 Bot 的另一条 Todo） | 弹窗说明，文案为「另一段 Bot 对话的改动还没提交」 |

> 说明：同一 Bot 在另一条 Todo 下留下的改动，也按「其他会话」处理，因为当前会话并不知道那些改动的来历。

### 6.4 弹窗文案示例

> 这个目录里有 6 个文件还没提交，其中有你自己的改动。Bot 直接在这里改，它的改动会和你的混在一起，事后很难分清哪些是它改的。
> 建议在独立 worktree 里做：会带上你未提交的改动，让它看到的和你一致；但你的目录不会被改动，结果放在单独的分支上，你看过再合并。
>
> [开 worktree]　[仍在当前目录跑]

### 6.5 worktree 的做法

- 位置：`~/Library/Application Support/com.edanhuang.easydo/worktrees/<bot>/<todo>`。
- 分支名：`easydo/<bot 名>/<todo id 前 8 位>`。
- 创建时把原目录未提交的改动（已跟踪文件的修改 + 未跟踪文件）复制进 worktree，保证 Bot 看到的和用户一致；原目录不写入任何东西。
- 运行结束后，Bot 没提交的改动自动提交到该分支，不丢失。
- 该会话后续运行都在这个 worktree 里（见 5.2）。
- Todo 完成或归档后删除 worktree 目录，分支保留，由用户决定合并或删除。

## 7. 运行

### 7.1 调用方式

| | Claude Code | Codex |
|---|---|---|
| 新会话 | `claude -p --output-format stream-json --verbose --permission-mode bypassPermissions --model <模型> -n <标题> --append-system-prompt <说明> <提示词>` | `codex exec --json -m <模型> --dangerously-bypass-approvals-and-sandbox -C <目录> -o <结果文件> <提示词>` |
| 延续 | 加 `--resume <会话ID>` | `codex exec resume --json -m <模型> --dangerously-bypass-approvals-and-sandbox -o <结果文件> <会话ID> <提示词>` |
| 会话 ID | 输出流的初始化事件 | `thread.started` 事件的 `thread_id` |
| 最终回复 | 输出流最后的结果事件 | `-o` 写出的文件；或最后一个 `item.completed` 中 `item.type = agent_message` 的 `text` |
| Token 用量 | 结果事件里的用量和费用 | `turn.completed` 事件的 `usage` |
| 失败判断 | 结果事件的错误标记和进程退出码 | 进程退出码和 `turn.failed` 事件 |

**Codex 实测结论**（codex-cli 0.163.0）：

- 事件流依次是 `thread.started` → `turn.started` → 若干 `item.completed`（`item.type` 有 `agent_message`、`error` 等）→ `turn.completed`。
- `usage` 字段：`input_tokens`、`cached_input_tokens`、`cache_write_input_tokens`、`output_tokens`、`reasoning_output_tokens`。没有费用字段，Bot 页面对 Codex 只展示 token 数。
- **续会话时 `usage` 是整个会话的累计值，不是本次的**：第一次运行 `input_tokens` 为 20682，续一次后为 41381，而那一次实际只用了 20699。所以每次运行的用量要用「本次累计值 − 上次记录的累计值」算出来。
- `item.type = error` 不代表运行失败：本机 Codex 配置里有一项不识别的设置，每次都会输出两条这样的警告，但运行正常完成。失败只看退出码和 `turn.failed`。
- `codex exec resume` 不接受 `-C` 和 `-s`，工作目录沿用会话创建时的目录；EasyDo 启动续会话的进程时，进程工作目录也设成会话记录的目录。
- 不在 git 仓库里时需要加 `--skip-git-repo-check`。

**附加说明不写进用户目录**：multica 把说明写成工作目录里的 `CLAUDE.md`，因为它的工作目录归自己管；EasyDo 的 Bot 目录是用户自己的仓库，所以 Claude 走 `--append-system-prompt`，Codex 拼在提示词前面。说明内容：

- 本次处理的 Todo 内容和 id；
- 按 easydo Skill 的规则，确实需要时用 `easydo update` 修改这条 Todo，不需要就不动；
- 最后一段回复写给用户看：交代结果，需要用户决定的事讲清楚。

### 7.2 权限

`bypassPermissions` 意味着 AI 可以在工作目录里执行任何命令。因此目录必须由用户在 Bot 上明确选择，EasyDo 不提供默认目录。

### 7.3 状态

| 状态 | 含义 |
|---|---|
| 运行中 | 进程在跑 |
| 已完成 | 正常结束，拿到最终回复 |
| 失败 | AI 报错退出，或被看门狗判定卡死 |
| 已停止 | 用户手动停止 |
| 已中断 | 进程中途被结束、输出里没有结束事件；因为会话 ID 还在，下次可以接着派发 |

- **看门狗**：不设总时长上限；连续一段时间（默认 30 分钟）没有任何输出才判定卡死并结束进程。
- **并发**：全局同时运行数设上限（默认 3），超出时派发按钮提示稍后再试。
- **EasyDo 退出**：不结束 Bot，不需要守护进程。Bot 进程的输出直接写进 `bot-runs/<运行ID>.jsonl`（和数据库同目录），EasyDo 一边写一边读；退出后 Bot 照常跑完。有 Bot 在运行时按 ⌘Q 或关窗口会先弹窗确认（应用菜单里的「退出」换成了自己的菜单项，程序坞右键退出拦不住）。
- **EasyDo 启动**：对还标着「运行中」的任务，用记下的 pid 和进程启动时间（防 pid 复用）判断：
  - 进程还在：接着读输出文件，卡片上照常显示运行中；
  - 进程已结束：读完文件，按里面的结束事件记为完成或失败，照常发消息；
  - 文件里没有结束事件：记为「已中断」，可以接着派发继续。
- 输出文件在结果同步后删除。

### 7.4 停止

右键菜单在运行中显示「停止 Bot」。停止后状态为已停止，不产生结果消息。

## 8. 看板上的表现

### 8.1 运行中

| | 表现 |
|---|---|
| 列表 | 行首完成按钮的位置换成 Bot 头像（Bot 颜色的机器人图标），外圈有呼吸动效 |
| 画布 | 卡片外侧左上角显示「头像 + 名字 + 动效」，卡片投影换成 Bot 的颜色 |

动效遵循系统的「减少动态效果」设置，开启时改为静态。

### 8.2 运行中禁止完成和归档

不希望 Bot 执行中 Todo 被完成。运行中：

- 完成按钮被头像占位；
- 右键菜单的「完成」「归档」置灰，提示「Bot 运行中，先停止」。

### 8.3 结束后

- 列表恢复完成按钮，画布去掉 Bot 标记和彩色投影。
- Todo 内容只在 Bot 认为需要时由它通过 `easydo update` 修改，与 easydo Skill 的逻辑一致；EasyDo 不额外往 Todo 里写结果或决策提示。
- Bot 的最终回复作为本次运行的结果，存成一条未读消息。

## 9. 消息

### 9.1 内容

只保存需要交回 EasyDo 的东西：

- 用户发出的说明（派发时的补充说明、会话窗里的回复）；
- 每次运行的最终回复；
- 运行失败、中断、换成新会话这类提示。

完整过程输出不保存。会话窗展示会话标题和会话 ID，方便到对应 AI 的 App 里找到原会话。

### 9.2 消息抽屉

**全局入口**：顶栏右侧放一个消息按钮（信封图标），带全部未读的总数，点击打开抽屉，浏览所有会话。每行 Todo 上的信封只负责跳到对应会话。

从右侧滑出，分三层：

1. Bot 列表；
2. 该 Bot 名下有过对话的 Todo；
3. 这对 Todo × Bot 的对话。

对话窗底部有输入框，发送后用同一会话再运行一次；运行中输入框不可用。

### 9.3 未读提示

| | 位置 |
|---|---|
| 列表 | 每行 Todo 的右上角：信封 + 未读数 |
| 画布 | 卡片外侧左上角常驻；与运行中的 Bot 标记同时出现时，从左到右按优先级从小到大排列：Bot 标记（1）在左，信封（2）在右 |

- 信封和未读数做成一个圆角长方形（高 18px、圆角 4px）：底色用主题重点色（铁锈红），图标和数字用重点色上的反色。
- **列表行右侧的排列**：
  - 有未读时，信封常驻在最右边，不随悬停移动。
  - 信封左边（没有信封时就是最右边）是操作按钮区，悬停才显示，例如归档。
  - 按钮区固定预留一个按钮的宽度，平时不可见但占位，悬停时正文不会重排。
  - 以后按钮多于一个时，悬停时向左展开，盖在正文末尾上（带行悬停底色），正文依然不重排。
  - Bot 运行中不能归档，按钮区为空，但仍然占位，信封照常显示。
- 点击信封打开消息抽屉，直接定位到对应 Bot、对应 Todo 的会话窗。
- 打开会话窗即视为已读，信封消失。

### 9.4 归档与删除

- Todo 归档时，它的消息一起归档；消息不支持单独归档。
- 归档的 Todo 被恢复时，消息一起恢复。
- 收件箱的 Todo 到期被自动删除时，消息一起删除。

## 10. 数据

| 表 | 主要字段 |
|---|---|
| `bots` | id、名称、颜色、AI、模型、目录、创建 / 更新时间 |
| `bot_sessions` | Todo id、Bot id（联合唯一）、AI、会话 ID、会话标题、实际工作目录、是否 worktree、分支名 |
| `bot_runs` | id、会话、状态、开始 / 结束时间、输入 / 输出 / 缓存 token、费用、错误信息 |
| `bot_messages` | id、会话、所属运行、发送方（用户 / Bot / 系统）、内容、创建时间、已读时间、归档时间 |

## 11. 从 multica 借鉴的设计

| multica 的做法 | EasyDo 中的对应 |
|---|---|
| 统一的执行接口：给提示词，返回事件流和结果（完成 / 失败 / 中止 / 超时 / 取消） | 第 7 节，Claude 和 Codex 走同一套运行流程 |
| 保存会话 ID，后续用 `--resume` 续上 | 第 5 节，按 Todo × Bot 复用 |
| AI 通过与人相同的 CLI 回写系统 | Bot 通过 `easydo update` 改 Todo |
| 每个任务一个 worktree，带上用户未提交的改动，用户目录不写入，结果以分支交付 | 第 6 节，但默认关闭，按改动归属征得同意后开启 |
| 用空闲看门狗代替硬超时 | 7.3 |
| 并发上限 | 7.3 |
| 只在需要人决定时提醒 | 未读消息只来自最终回复 |

没有采用的：多机运行时、团队与权限、执行过程完整回放、运行中插话、自动重试、定时派发。

## 13. 小石头（侧栏桌宠）

不指定 Todo，用一句话让 Bot 维护已有的 Todo，例如「把暂停营业那条和重试 job 那条归档」。

- **样子**：一颗暖石色的鹅卵石（42×30），只有两只眼睛，界面上不配名字和状态文字，状态全靠眼睛和动作：
  - 空闲时浮动、眨眼；悬停时眯成月牙眼、一蹦一蹦。
  - 处理中皱着眉、睁眼盯着身前的小键盘，两只小手轮流敲；这时眼睛不跟着气泡转。
  - 处理完看结果：这一轮成功执行过 easydo 命令就眯眼开心；什么都没执行成功（或运行失败）就一大一小两只眼、脸侧冒个问号。手动停止和中断不做表情。
  - 有新回复时右上角亮一个重点色小点。
- **位置**：窗口左下角只有一个小石头。侧栏展开时坐在底栏分隔线上；收起时斜 45° 趴在窗口左边缘，露出眼睛，悬停时多探出来一点并挥动一个小圆点招手。侧栏宽度和它的位置、角度用同样的时长过渡，收起展开时它在两处之间飞过去。
- **对话气泡**：点小石头（展开、收起状态都一样）打开气泡，开在它头顶上方、尖角朝下指着它，它抬眼看着气泡；侧栏展开时气泡从侧栏里越过边缘长到看板上方，收起时跟着它贴到窗口边缘，切换侧栏时一起滑过去。外形和底部录入框同一套平滑圆角、发丝线描边，尖角和气泡是同一条轮廓。不加遮罩，开着时看板照常能看能点。
  - 空着时整个气泡是一条胶囊输入框；有对话后向上长高，回复直接是正文，自己说的话垫一块浅底。输入行右边有「新对话」，处理中换成「停止」，回复的位置只有一支来回写的笔。
  - 处理中照样能打字，回车和发送键不发，等处理完再发。重新打开时光标在草稿末尾。
  - 按 Esc、再点小石头收起；输入框空着时点别处也会收起，写了内容的不收。
- **数据**：小石头是 `bots` 表里 `kind = 'steward'` 的一行，不出现在 Bot 页面和派发菜单里。它的会话 `todo_id` 为空（旧库的 `bot_sessions` 为此重建过一次表），会话、运行、消息沿用派发的表。同一时间只有一段当前会话（最新建的那段），「新对话」时另起一段，旧的留在库里不再显示。
- **工作目录**：由 EasyDo 管，固定在数据目录下的 `steward/`，只用来存会话，用户不用选。
- **权限**：只接 Claude Code。内置工具只开 Bash，`--permission-mode dontAsk` 加 `--allowedTools "Bash(easydo *)"`，只放行 easydo 命令，其余一律拒绝；不加载 MCP。
- **提示词**：每次运行附带此刻的看板摘要（进行中的全部 Todo，加上最近 24 小时完成或归档的，每条一行：id 前 8 位、分组、最后更新、首句）。能唯一对上就直接执行，对上多条或拿不准时列出候选问用户；不删除 Todo；最后一段逐条列出动了哪些 Todo。它加载不了 Skill，所以 easydo Skill 的「Todo 内容写法」一节原文也放进提示词（取自随 App 打包的 `skills/easydo/SKILL.md`），并要求多行内容用 `$'…\n…'` 传给 `--detail`。用户说「改成……」时改写当前进度而不是追加，被取代的旧待办删掉或勾掉，拿不准就问。回复要短：第一句说结果、用 Todo 首句指代而不报 id，闲聊不写「没有改动」之类的套话。
- **结果判断**：解析 Claude 的事件流，`tool_result` 没标错就算一次成功执行；运行结束时记在 `bot_runs.acted`，小石头据此做开心或疑问的表情。
- **和派发的关系**：小石头的运行不占派发的并发名额，也不算进退出确认里的运行数。某条 Todo 有 Bot 在跑时，小石头同样不能完成或归档它，会把原因告诉用户。跑完发 `bot-runs-changed`，看板跟着刷新。
